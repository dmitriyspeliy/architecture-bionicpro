# Задание 1. Архитектурное решение по управлению учётными данными

## Решение

Для аутентификации вводится отдельный backend-for-frontend `bionicpro-auth`. Frontend не является владельцем OAuth-токенов и не получает `access_token` и `refresh_token`. Он инициирует вход через `bionicpro-auth` и после успешной аутентификации получает только серверную session cookie с атрибутами `HttpOnly`, `Secure` и `SameSite`.

`bionicpro-auth` выполняет Authorization Code Flow с PKCE через Keycloak, обменивает authorization code на токены по back-channel и хранит токены в серверном Session Store. `access_token` и `refresh_token` привязываются к идентификатору сессии; `refresh_token` хранится в зашифрованном виде. При истечении `access_token` сервис обновляет его самостоятельно.

Keycloak используется как единая точка аутентификации и Identity Broker. Для каждого представительства подключается локальный источник учётных данных: OpenLDAP через User Federation либо внешний OIDC/OAuth 2.0 Identity Provider. Региональные роли преобразуются в единую модель ролей BionicPRO.

Персональные, медицинские и авторизационные данные хранятся в региональном контуре страны представительства. Между регионами допускается передача только минимального технического идентификатора, нормализованных ролей и данных, разрешённых законодательством и согласием пользователя.

## Основные потоки

1. Пользователь обращается к frontend, который перенаправляет его на `bionicpro-auth`.
2. `bionicpro-auth` инициирует Authorization Code Flow с PKCE в Keycloak.
3. Keycloak выполняет аутентификацию через региональный OpenLDAP или внешний IdP.
4. `bionicpro-auth` получает токены по серверному каналу, сохраняет их в Session Store и возвращает frontend только session cookie.
5. При обращении к защищённому API `bionicpro-auth` получает токены по session id и передаёт `access_token` только по внутреннему каналу.
6. API проверяет принадлежность протеза пользователю до чтения отчётов и медицинских данных.

## Принятые решения безопасности

- OAuth 2.0 Authorization Code Flow с PKCE `S256`.
- Отсутствие OAuth-токенов в браузере, `localStorage` и `sessionStorage`.
- Серверное хранение и привязка токенов к сессии.
- Ротация session id после успешной проверки защищённого запроса.
- `HttpOnly`, `Secure`, `SameSite` для session cookie.
- LDAPS для подключения Keycloak к OpenLDAP.
- Региональная изоляция персональных и медицинских данных.
- Identity Brokering для подключения удостоверяющих служб разных стран.
